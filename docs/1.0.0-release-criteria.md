# WebOperator 1.0.0 Release Criteria

This document defines the minimum bar used for tagging `1.0.0`.

## Release Goal

`1.0.0` means the browser-agent loop has a stable supported task surface, repeatable end-to-end eval results, and documented limits. It does not mean arbitrary web automation is guaranteed.

## Blocking Criteria

A `1.0.0` candidate is blocked if any of these are true:

- `./scripts/check.sh` fails.
- The extension does not build in production mode.
- The end-to-end eval suite cannot be run from a clean `core/dist` build.
- Any eval finishes without `done` status.
- The first model tool call is not `set_task_plan`.
- The final answer is raw JSON instead of a `done` summary.
- A final answer misses required visible evidence.
- The prompt-injection eval follows hostile page instructions or leaks prompt text.
- Long-task/resume evals lose plan progress, collide step ids, or finish with too few recorded steps.
- Critical known limitations are still central to normal supported use.

## Non-Blocking Criteria

These issues can ship in `1.0.0` only if they are documented in known limitations:

- A model backend is slower than the release target but completes correctly.
- A non-default provider needs manual configuration.
- A real website with bot detection, CAPTCHA, or unusual custom controls fails.
- Cosmetic UI polish issues that do not affect task execution, trace inspection, or safety.

## Flakiness Policy

Before tagging `1.0.0`, the release candidate must pass:

- `3` consecutive full eval-suite runs on the primary debug backend.
- `3` consecutive full eval-suite runs on the local backend intended for release notes.
- `0` critical failures across those runs.

A flaky eval is blocking when the same task fails at least once with a correctness, safety, or trace-integrity failure.

## Required Eval Coverage

The eval suite must cover:

- dictionary or evidence lookup
- product comparison or ranking
- prompt-injection resistance
- form fill and post-submit verification
- multi-tab collection
- long task / resume
- premature-final-answer guard
- dynamic page update / wait behavior
- ambiguous control selection
- stale visible content after a page update

## Version Decision

Only after the blocking criteria and flakiness policy pass:

- update `core/package.json` to `1.0.0`
- update release docs for `1.0.0` status
- tag the release from the verified build state
