# Техническое задание (ред. 2)

## Локальный браузерный агент-расширение для Chrome на базе Gemma 4 через Ollama

**Версия:** 0.2 (MVP)
**Дата:** 20 апреля 2026
**Изменения относительно ред. 1:** переход на семейство моделей Gemma 4 как единственную runtime-модель (вместо связки текстовой + vision). Убран отдельный vision-пайплайн, упрощена архитектура, пересмотрены пороги производительности, добавлено использование нативного function calling и thinking mode.

---

## 1. Общие сведения

### 1.1. Назначение
Chrome-расширение, реализующее автономного агента управления веб-страницами под руководством локальной мультимодальной LLM семейства Gemma 4, запускаемой через Ollama на машине пользователя.

### 1.2. Цель
Делегирование произвольных задач в браузере локальному агенту, без передачи данных третьим сторонам.

### 1.3. Принципы
- **Локальность.** Инференс и все данные пользователя не покидают машину.
- **Единая мультимодальная модель.** Gemma 4 обрабатывает текст и изображения в одном вызове, что устраняет разделение на «текстовый канал» и «vision-канал».
- **Native tooling.** Агент использует встроенный function calling Gemma 4 вместо ручного парсинга JSON из свободного текста.
- **Адаптивный thinking.** Thinking mode включается по правилам, а не безусловно — экономит время на простых шагах.
- **Экономия вызовов.** Кэш действий, кэш снэпшотов, компактизация контекста.
- **Наблюдаемость.** Полный лог каждого шага.

---

## 2. Целевые сценарии

### 2.1. Поддерживаемые
- Навигация, клики, ввод, выбор, загрузки/скачивания.
- Многошаговые задачи с рассуждением.
- Работа с формами.
- Извлечение данных со страницы и сводка для пользователя.
- Визуальная верификация результата действия (через мультимодальный вызов той же модели).

### 2.2. Вне объёма MVP
Обход капч, аутентификация из расширения, параллельные вкладки, сложные canvas-приложения.

---

## 3. Архитектура

### 3.1. Компоненты

| Компонент | Роль |
|---|---|
| Service Worker (MV3) | Цикл агента, координация с Ollama, состояние, кэш. |
| Content Script | A11y-снэпшот, нумерация refs, Set-of-Mark оверлей, выполнение действий в DOM. |
| CDP-драйвер | `chrome.debugger`: клики по координатам, клавиатура, скриншоты. |
| Side Panel UI | Ввод задачи, лог шагов, подтверждение критичных действий, настройки. |
| Gemma 4 Client | HTTP-клиент к Ollama: chat-эндпоинт с tools, мультимодальный ввод (image_b64 + text), thinking mode флаг. |
| Storage | `chrome.storage.local` для настроек, IndexedDB для кэша, логов, скриншотов. |

### 3.2. Профили моделей

Профиль задаётся пользователем в настройках. Один профиль = одна модель Gemma 4 для всей работы агента (рассуждение, действия, vision — всё в ней).

| Профиль | Модель | Требуемое железо | Назначение |
|---|---|---|---|
| **Edge** | `gemma4:e2b` | 2–4 ГБ RAM/VRAM | Слабые машины, ноутбуки без дискретной GPU, простые задачи. Thinking mode off по умолчанию. |
| **Balanced** (default) | `gemma4:e4b` | 4–8 ГБ VRAM или unified memory | Основной сценарий: смартфон-класс железа, Apple Silicon M1+, RTX 3050+. |
| **Fast** | `gemma4:26b-a4b` (MoE) | 16+ ГБ VRAM | Быстрый инференс благодаря 4B активных параметров, но качество 26B. Топовый выбор на RTX 4070+/M2 Pro+. |
| **Quality** | `gemma4:31b` | 24+ ГБ VRAM | Сложные многошаговые задачи, длинный контекст, ранжирование open-моделей на уровне топов. |

Thinking mode включается автоматически на шагах, которые модель пометила как неоднозначные (нужна переоценка), при ретраях и при планировании задачи. На рутинных кликах — отключается для скорости.

### 3.3. Цикл работы

1. Пользователь вводит задачу.
2. Service Worker строит план через Gemma 4 с включённым thinking mode (декомпозиция на шаги).
3. На каждом шаге:
   - Content Script собирает a11y-снэпшот с refs (`@e1, @e2, …`).
   - Проверяется кэш действий `(url_pattern, intent_hash, dom_hash)`. Попадание — выполнить без LLM.
   - При промахе — формируется мультимодальный запрос к Gemma 4: система-промпт с описанием инструментов (tools) + a11y-снэпшот как текст + скриншот с Set-of-Mark как изображение (опционально, по правилам). Thinking mode — по политике.
   - Ответ возвращается как tool call с параметрами действия. JSON-валидатор уже не нужен — function calling обеспечивает контракт на уровне рантайма Ollama.
   - Действие выполняется через DOM/CDP.
   - Верификация результата: диффф снэпшотов; при неоднозначности — скриншот + спросить модель.
4. Цикл до `done` или фэйла.
5. Удачная последовательность пишется в кэш.

### 3.4. Правила подключения скриншота

Скриншот с Set-of-Mark включается в мультимодальный запрос, если:
- A11y-снэпшот пуст (canvas, shadow DOM без проброса в a11y);
- Шаг помечен как «визуальная верификация» (модель так решила на предыдущем шаге);
- Страница в iframe без доступа к структуре;
- Пользователь явно включил «always-vision» в настройках (для сложных сайтов).

На стандартных веб-страницах — только a11y-снэпшот. Это ключевая оптимизация: мультимодальный вызов даже на одной модели дороже чисто текстового.

## 4. Функциональные требования

### 4.1. Accessibility snapshot
- **FR-1.** Плоский список интерактивных элементов с `ref, role, name, value, state, bbox`.
- **FR-2.** Стабильные refs `@eN` в рамках снэпшота.
- **FR-3.** Кэш по `dom_hash` + URL.
- **FR-4.** Ограничение по размеру: элементы вне вьюпорта — по запросу.

### 4.2. Выполнение действий
- **FR-5.** Набор действий: `click`, `type`, `select`, `scroll`, `navigate`, `wait`, `extract`, `done`.
- **FR-6.** Клик приоритетно через DOM, fallback на CDP по координатам.
- **FR-7.** Ввод через CDP keyboard events (не в `value` напрямую).
- **FR-8.** Таймаут на действие 10 с, перехват исключений.

### 4.3. Set-of-Mark и мультимодальный режим
- **FR-9.** Оверлей с номерными маркерами интерактивных элементов, refs совпадают с a11y-снэпшотом.
- **FR-10.** Скриншот прикрепляется к запросу Gemma 4 в формате base64, размер кадрируется до вьюпорта, даунсемпл до 1024px по длинной стороне (баланс детализации и скорости).
- **FR-11.** Бюджет визуальных токенов Gemma 4 — 280 по умолчанию (из поддерживаемых 70/140/280/560/1120), повышается до 560 при явной «визуальной верификации».
- **FR-12.** Правила автоподключения скриншота — см. 3.4.

### 4.4. Интеграция с Gemma 4 через Ollama
- **FR-13.** URL Ollama настраивается (default `http://localhost:11434`).
- **FR-14.** Выбор профиля модели из списка 3.2.
- **FR-15.** Используется native function calling: инструменты `click`, `type`, `select`, `scroll`, `navigate`, `wait`, `extract`, `done` регистрируются как tools с JSON-схемами параметров.
- **FR-16.** Thinking mode включается флагом в запросе; политика: on для планирования, on для ретраев, on при `need_reasoning: true` из предыдущего шага, off в остальных случаях.
- **FR-17.** Native system prompt используется для постоянной части инструкций агента; история пользовательских команд и наблюдений идёт в user-сообщения.
- **FR-18.** Стриминг ответа в UI (виден thinking-блок, если включён).
- **FR-19.** При недоступности Ollama — понятное сообщение и инструкция по установке модели (`ollama pull gemma4:e4b` и т.д.).
- **FR-20.** В истории диалога не сохраняется содержимое thinking-блоков предыдущих ходов — только финальные tool calls (требование модели для корректной работы multi-turn).

### 4.5. Кэш действий
- **FR-21.** Ключ: `(url_pattern, intent_hash, dom_structure_hash)`.
- **FR-22.** Значение: последовательность tool calls и ожидаемый финальный снэпшот.
- **FR-23.** Воспроизведение без LLM с верификацией; при несовпадении — инвалидация и решение заново.
- **FR-24.** TTL 30 дней, ручная очистка.

### 4.6. Безопасность
- **FR-25.** Подтверждение критичных действий (Delete/Pay/Submit/Удалить/Оплатить) в UI. Список настраиваемый.
- **FR-26.** Белый/чёрный список доменов.
- **FR-27.** Никаких исходящих запросов, кроме настроенного Ollama-эндпоинта. Проверяется на уровне manifest permissions (`host_permissions` не содержит wildcard внешних доменов).
- **FR-28.** Prompt injection через DOM: system prompt жёстко разделяет инструкции пользователя и наблюдения со страницы (разные блоки с явной маркировкой «UNTRUSTED PAGE CONTENT»); критичные действия требуют подтверждения.

### 4.7. UI
- **FR-29.** Side Panel: ввод задачи, Start/Pause/Stop, список шагов.
- **FR-30.** Клик по шагу — полный промпт, thinking-блок (если был), tool call, скриншот (если был), DOM-снэпшот.
- **FR-31.** Настройки: URL Ollama, профиль модели, политика thinking, политика скриншотов, таймауты, white/black-листы, очистка кэша, бюджет визуальных токенов.
- **FR-32.** История задач, повтор, экспорт трассировки в JSON.

### 4.8. Наблюдаемость
- **FR-33.** Каждый шаг: входной снэпшот, промпт, thinking (если есть), tool call, результат, дельта состояния, тайминги, профиль модели.
- **FR-34.** Экспорт трассировки одним файлом (JSON + сжатые PNG).

## 5. Нефункциональные требования

### 5.1. Производительность (целевые, на Balanced профиле `gemma4:e4b`, 8 ГБ VRAM)

| Операция | Целевая латенси |
|---|---|
| Шаг без скриншота, без thinking | ≤ 2 с |
| Шаг со скриншотом (мультимодальный вызов), без thinking | ≤ 5 с |
| Шаг с thinking mode | ≤ 8 с |
| Планирование задачи (один раз в начале, thinking on) | ≤ 15 с |
| Попадание в кэш действий | ≤ 500 мс |
| Построение a11y-снэпшота | ≤ 300 мс |

Для Fast профиля (26B A4B на 16+ ГБ VRAM) — пороги умножаются на 0.7 за счёт MoE-архитектуры. Для Edge профиля (E2B) — на 1.5.

### 5.2. Совместимость
- Chrome стабильной ветки, Manifest V3.
- Windows 10/11, macOS 13+, Ubuntu 22.04+.
- Ollama с поддержкой Gemma 4 (day-one из релиза).

### 5.3. Ресурсы
- Расширение: ≤ 100 МБ распакованное, ≤ 50 МБ RAM в idle.
- IndexedDB: лимит 2 ГБ с ротацией по возрасту.
- Модель: отдельно через Ollama, расширение не шипит веса.

### 5.4. Надёжность
- 3 ретрая на шаг с переформулировкой, затем запрос пользователю.
- Отказ Ollama — пауза задачи с возможностью возобновления.

### 5.5. Приватность
- Нет телеметрии.
- Пароли и `type=password` маскируются в логах и трассировках.
- Экспорт логов — только по явному действию.

## 6. Технологический стек

- **Расширение:** TypeScript, Manifest V3, Vite, React для UI.
- **Chrome API:** `chrome.debugger`, `chrome.scripting`, `chrome.storage`, `chrome.tabs`, `chrome.sidePanel`.
- **Инференс:** Ollama, REST `http://localhost:11434`, chat-эндпоинт с tools и images.
- **Модели:** семейство Gemma 4 (`e2b`, `e4b`, `26b-a4b`, `31b`), выбираются профилем.
- **Хранилище:** IndexedDB (Dexie) + `chrome.storage.local`.
- **Тестирование:** Vitest, Playwright.

## 7. Этапы разработки

### Этап 1. Ядро на Gemma 4 (4 недели)
A11y-снэпшот, refs, базовые действия, Ollama-клиент с function calling, system prompt, минимальный UI, лог. Один профиль (Balanced, `e4b`). Thinking mode вручную on/off. Критерий: три сценария (поиск в Wikipedia, форма, e-commerce навигация) успешно проходят.

### Этап 2. Мультимодальность и устойчивость (3 недели)
Set-of-Mark, скриншоты в запросах, правила автоподключения, кэш действий, верификация, подтверждение критичных действий, чёрный/белый список. Критерий: сценарии из Этапа 1 повторно проходят через кэш без вызовов LLM. Добавляется сценарий с canvas — проходит через скриншот.

### Этап 3. Профили и оптимизации (2 недели)
Переключение профилей (E2B/E4B/26B A4B/31B), адаптивный thinking (авто-on/off), бюджет визуальных токенов, бенчмарк латенси на каждом профиле. Критерий: все пороги из NFR-5.1 выполняются на референсном железе.

### Этап 4. Полировка (2 недели)
Экспорт трассировок, история задач, экран настроек, документация, маскирование паролей. Критерий: чек-лист NFR пройден.

**Итого:** 11 недель до первого внутреннего релиза (сократилось на 1 неделю за счёт отсутствия отдельного vision-пайплайна).

## 8. Риски

| Риск | Митигация |
|---|---|
| E2B/E4B недостаточно сильны для сложного многошагового планирования. | Адаптивное переключение на тяжёлый профиль только на шаге планирования (26B/31B через второй процесс Ollama, если доступно), короткие шаги, thinking mode on для планирования. |
| Мультимодальный вызов дороже чисто текстового даже на одной модели. | Скриншот подключается только по правилам 3.4, не на каждом шаге. Бюджет визуальных токенов — 280 по умолчанию. |
| Manifest V3 service worker засыпает. | Состояние агента — в IndexedDB, цикл на событиях, пробуждение по `chrome.alarms`. |
| `chrome.debugger` показывает жёлтую плашку. | Документировано; для простых кликов использовать DOM API без CDP. |
| Prompt injection через скрытый текст в DOM. | Явное разделение trusted/untrusted блоков в system prompt, обязательное подтверждение критичных действий, white-лист доверенных доменов для автономного режима. |
| Thinking mode в multi-turn: если оставить thoughts в истории, модель деградирует. | Реализовано FR-20 — thoughts отбрасываются перед следующим user turn. |
| Vision Gemma 4 может быть слабее на Set-of-Mark-разметке, чем специализированные vision-модели. | Бенчмарк на этапе 3; если качество недостаточное — добавить специализированную visual-модель опционально, как было в ред. 1. |

## 9. Приёмка

Система принимается, если:
1. Все FR реализованы и покрыты автотестами.
2. NFR-пороги достигнуты на референсном железе для каждого из четырёх профилей.
3. 20 эталонных сценариев: успешность ≥ 80% на холодном запуске, ≥ 95% на кэшированном.
4. Аудит кода: нет исходящих HTTP-запросов, кроме настроенного Ollama.
5. Каждый профиль модели (E2B, E4B, 26B A4B, 31B) протестирован на подмножестве сценариев, подходящих его классу сложности.
